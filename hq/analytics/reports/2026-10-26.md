## Investigation 1: the "jeans" search burst (resolved, benign)

While pulling the 7-day search sample, one query stood out: ~70 rows for
`query = "jeans"` from a single `anonymous_user_id`
(`d71175a6-007c-4bc0-ad66-1dbb4beb9056`), several with sub-second gaps —
enough to look like a bot loop or a duplicate-event-firing bug.

Traced it by pulling that visitor's full event history: 76 events total
over ~2.5 hours (01:25–03:48 UTC), broken down as 6 `page_view`, 3
`page_performance`, 5 `search`, and 62 `product_impression`. The
`product_impression` rows legitimately carry the active search `query`
value for attribution — so "70 rows for query=jeans" is really "one
visitor searched jeans 5 times and saw 62 product cards while browsing
the results," not a tracking bug or bot. No `set_visitor_flag` action
warranted (nowhere near the outbound-click threshold, and this isn't the
kind of activity that threshold is for). Logging this so a future run
doesn't re-chase the same false alarm.

## Investigation 2: `broken_image` volatility — real root cause found

Prior check-ins noted `broken_image` bouncing between ~10% and ~22% of
daily events and treated it as noise/"someone else's problem eventually."
Decided to actually quantify it this run instead of re-noting the same
vague observation.

First pass gave a misleading answer: a naive 7-day pull without
pagination silently hit PostgREST's 1000-row default page cap, making
the data look thin and random. Redid it with exact-count range queries
per day (`Prefer: count=exact`, `Range: 0-0`) to get accurate daily
totals:

| Day | Total events | broken_image | % |
|---|---|---|---|
| 10-19 | 270 | 3 | 1.1% |
| 10-20 | 1613 | 95 | 5.9% |
| 10-21 | 766 | 48 | 6.3% |
| 10-22 | 522 | 26 | 5.0% |
| 10-23 | 1355 | 111 | 8.2% |
| 10-24 | 487 | 106 | 21.8% |
| 10-25 | 1187 | 196 | 16.5% |

Then pulled all 589 `broken_image` rows from the last 7 days and grouped
by page and session: only **21 distinct pages** account for every one of
them, and each day's count is driven by just **4-5 real sessions**
happening to browse one of those specific pages (one session alone can
generate 50-99 events scrolling a product's image gallery where every
photo 404s). That's why the daily percentage looks erratic — it's not a
growing site-wide rate, it's whether a visitor happened to land on one of
a fixed, small set of broken pages that day.

Sample `metadata.src` values point at dead `cdn.shopify.com` URLs
(product images removed/renamed/moved on the brand's own Shopify store
since the last feed pull), concentrated in a handful of brands —
`racer-worldwide` (3 separate broken products — looks brand-wide, not
one-off), `namedcollective`, `coldcultureworldwide`, `colebuxton`,
`moremoneymorelove`, `str4wrld`. A couple of the affected images do route
through `img.streetdotcom.com` (imgproxy), worth a closer look for those
specifically.

Filed as a Tier 2 question for Catalog via GM in `questions.md` with the
full page list and brand breakdown. Updated `charter.md`'s Known Gotchas
to replace the old "noisy, not escalating" framing with this root cause.

### Investigation: `results_count: 1000` on a "jeans" search — false alarm

While re-pulling the last 24h of `search` events, two rows for query
"jeans" (15 seconds apart, same visitor) both logged `results_count:
1000` — a suspiciously round number matching PostgREST's default
1000-row page cap that already caused a real miscount this morning
(`broken_image`). Worth checking before letting it pass.

Traced the actual code path (`lib/catalog-page.ts`'s `getCatalogPage` →
`searchProductsRanked` → the `search_products_ranked` Postgres RPC,
`supabase/migrations/20260924_search_products_ranked.sql`). Called the
RPC directly with the real expanded tsquery: `lib/catalog-ranking.ts`
treats "jean" and "denim" as a documented synonym pair (`{ broad: ["jean",
"denim"], specific: [] }`), so "jeans" actually searches `jean | denim`,
not just "jean". With explicit `p_limit` values of 2,000 and 50,000 (well
above 1,000), the RPC still returned exactly 1,000 rows every time for
`denim` alone, while an unrelated control query (`jean` alone) returned
162 — confirming 1,000 is `denim`'s genuine match count against the
current ~13,591-product active catalog (grown from the ~6,400 noted in
an August code comment), not a silently-capped value. No bug, no action
needed. Logging it so a future run doesn't re-chase this exact number.

### Self-directed: traffic-source → outbound-click conversion by source

No prior check-in has measured *conversion*, only *volume*, by traffic
source — and social growth is the current company priority, so this
felt like the highest-value thing to build this run rather than just
re-confirming clean numbers.

Method: pulled every `page_view` in the last 7 days, took each distinct
visitor's *first* page_view as their landing-attribution source
(classified by `utm_source` first, falling back to `referrer` hostname),
then checked whether that same `anonymous_user_id` ever logged an
`outbound_click` (`excluded=false`) anywhere in the same 7-day window.
335 distinct visitors, 24 of whom converted.

| Source | Visitors | Converted | Rate |
|---|---|---|---|
| direct/no-referrer | 136 | 5 | 3.7% |
| google organic | 127 | 14 | 11.0% |
| utm:ig | 32 | 1 | 3.1% |
| utm:chatgpt.com | 31 | 4 | 12.9% |
| android-app | 7 | 0 | 0.0% |
| instagram (referrer, no utm) | 1 | 0 | 0.0% |
| facebook | 1 | 0 | 0.0% |

Instagram (`utm:ig`) — the channel most tied to the social-growth
priority — converts to Street's core proof-of-value metric at roughly a
third the rate of organic Google search or ChatGPT referral traffic.
Framed this as a data point, not an alarm, in the question filed below:
32 visitors is a thin sample, social traffic is typically lower-intent
than someone searching for a specific item on Google, and this is the
first time anyone's pulled this number — recommended Growth-Social get a
second week's data before treating it as a trend.
