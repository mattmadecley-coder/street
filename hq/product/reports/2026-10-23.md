## What I found: git is unusable here, not just gh

`street-work/.git` is a worktree pointer file:

    gitdir: C:/Users/mattm/Documents/street/.git/worktrees/street-work

That's an absolute Windows path into the *other* checkout (`street`),
which isn't the folder connected to this session, and -- the actual
blocker -- this agent's shell is a sandboxed Linux VM with zero view of
the Windows filesystem (confirmed: no `/mnt/c`, no drive letters, nothing).
So no `git` command resolves at all: not `status`, `log`, `branch`,
nothing. Requesting access to `street` too wouldn't help, since a literal
`C:/Users/...` path still can't resolve inside a Linux VM either way.

This is almost certainly the same root cause behind Infrastructure's
`gh auth status` failure and missing-remote-URL problem from its own first
run today (`hq/infrastructure/reports/2026-10-23.md`), and matches the
line in my own agent definition about `gh` "cause not yet understood" --
it's one structural cause, not two separate flukes. Opened in
`questions.md` with a recommendation (make `street-work` a standalone
clone with its own `.git` + remote, not a worktree).

I deliberately did not: hand-edit `.git` internals to patch around it, or
write the new app code straight onto disk with no git to branch from --
both felt too likely to corrupt real history or land files on whatever
branch happens to be checked out, which is exactly what "never commit
directly to work or main" is guarding against even without a literal
`git commit`.

### git was not actually broken anymore -- the real remaining issue was line endings

Before touching anything, re-checked the git/worktree blocker from the
last two runs' questions.md entry. By the time this run started,
`street-work/.git` was already a real directory with a working `origin`
remote (not the worktree pointer file the first two runs hit) -- that
part had already been fixed, between this run and the last, by someone
or something else (see "Answered" in questions.md; this run didn't do
that fix). What was still broken: `git status` showed *every* tracked
file in the repo as modified, with every single line changed and
insertions exactly equal to deletions (`git diff --stat`: 446 files,
39097/39097) -- a textbook line-ending mismatch, not real changes.
Confirmed with a hex dump: HEAD's `package.json` is stored with `\n`,
the working-tree copy on disk has `\r\n`. `core.autocrlf` was unset in
this clone's local git config. `git config core.autocrlf true` fixed it
completely -- `git status` went to clean with zero commands that touch
file content. This is worth remembering for every future run in this
folder: a truly clean `git status` right after opening the shell is the
sign this is still configured correctly; hundreds of "modified" files is
the sign to check `core.autocrlf`, not to conclude git is broken.

`gh` is still not on `PATH` in this sandbox's `Bash` environment,
confirmed again this run (`which gh` -> not found). Followed the charter:
didn't fight it, planned to push the branch and write the PR description
into this report if `gh` stayed unavailable through the end of the run.

### The scheduling collision

While this run had `lib/admin-hq.ts` and the `app/admin/hq/**` files
staged as uncommitted changes on a branch (`agent/hq-office-page`, cut
from `origin/work`), `git status` suddenly showed a committed change
(`77b3db2`, "hq: weekly review 2026-10-23") sitting on top of that same
branch that this run never committed. Root cause: `street-work` is one
shared working directory with no isolation between department runs --
confirmed via `git reflog`, the GM's own weekly-review run committed
directly onto whatever branch happened to be checked out at that moment,
which was this run's branch, not `work`. A stale `.git/HEAD.lock` (timestamped
to the exact minute of that commit, no matching process running) also
sat in the way of this run's own next `git checkout`, left behind by
that same run apparently ending abruptly.

Treated this as data-preservation-first, not something to just force past:
saved the then-uncommitted tail edit to GM's own log line to `/tmp` before
touching anything (pure precaution; turned out to be re-derivable from
GM's own report anyway), pointed a plain branch ref at the foreign commit
so it couldn't be lost no matter what happened next, cleared the stale
lock (confirmed stale: no matching process, several minutes old, deletion
already approved for this session), and cut a fresh branch
(`agent/hq-office-page-v2`) from `origin/work` that carried forward only
this run's own uncommitted files, leaving the foreign commit exactly
where it already was so whoever's change it was could still find it.
Opened a new question about this in `questions.md` -- it's a structural
risk (two agents, one working directory, no locking) that goes well
beyond this one collision, and it isn't something Product should try to
fix unilaterally.
